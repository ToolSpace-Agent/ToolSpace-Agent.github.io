In one minute · Method overview

ToolSpace is a tool-centric environment synthesis pipeline.

Rather than synthesizing a database first and deriving tools from it, ToolSpace starts from how real tools actually compose — and lets environments and tasks emerge from that structure, in two stages:

1

Tool Space Exploration

Mine data / state / retry dependencies from adjacent calls in real execution traces with deterministic rules, building the weighted tool-composition graph \(\mathcal{G}_{TS}\). Tightly-coupled tools are clustered into environments — a database is synthesized only for state-mutating clusters; query tools restore snapshots, stateless tools replay cached returns.

2

Cross-Environment Verifiable Task Synthesis

Run state-aware random walks with rollback over \(\mathcal{G}_{TS}\): sample state-compatible successors \(\propto w\), execute step by step, roll back and resample on failure. Each completed chain is decompiled into a natural-language task with assertion-based verification, and kept only if it replays from \(s_0\).

The idea

Reverse the order:
tools first, environments second.

Data-centric synthesis presumes a realistic environment and derives tool composition from it — reversing the dependency that governs real agent execution. That inversion causes three failures, and ToolSpace is built to remove each one.

Before · Data-Centric

Database → Tools → Tasks

Theme→Synthesize 𝒟→Derive tools ℱe→Derive tasks
  • Tool–functionality mismatch. Tools reverse-synthesized from a fabricated database diverge from real interfaces.
  • Inauthentic orchestration. Links come from random linking or shallow LLM judgment — never witnessed in execution.
  • Single-environment ceiling. Tools are locked in their own sandboxes; cross-environment reachability is undefined.
VS
ToolSpace · Tool-Centric

Traces → Tool Graph → Environments → Tasks

Real traces ℳ→𝒢TS witnessed edges→Cluster = env→Random-walk tasks
  • Real interfaces, preserved. Tool definitions come from real MCP servers & agent corpora; only operation envs get a synthesized 𝒟.
  • Execution-witnessed edges. Every edge was seen between adjacent real calls, typed & weighted by frequency.
  • Cross-environment by construction. Walks cross clusters along witnessed edges — complexity grows with the space, not one sandbox.
Method

Three stages, one primitive:
witnessed tool composition.

Every retained training sample is a walk that actually executed — step by step, under real state transitions — and replayed cleanly from its initial snapshot.

🛰️

Tool Space Exploration

Collect real MCP & web agent trajectories, then mine adjacent calls with deterministic rules — shared arguments become data edges, state preconditions become state edges, repeated-after-failure calls become retry edges. Cluster the weighted graph into environments; synthesize a database only for operation clusters, restore snapshots for state-query tools, replay cached returns for stateless ones.

𝒢TS = (𝒱, ℰ, w) · 69 / 25 / 6 edge mix
🎲

State-Aware Random Walks + Rollback

From a tool bound to \((𝒟_k, s_0)\), repeatedly sample a state-compatible successor proportionally to edge weight and execute it. Every argument must trace to the task, \(s_0\), or an earlier return. A failed or relation-violating step restores \(s_{t-1}\) and resamples — chains that cannot proceed are discarded.

P(vt+1=v ∣ vt) = w(vt,v) / Σu w(vt,u)
✅

Decompile, Verify, Replay

Each successful walk \(\omega\) is decompiled into a natural-language task \(q\) (no tool names, no call order) plus assertions over final state, intermediate snapshots, and required output fields. The sample enters \(\mathcal{X}_{TS}\) only if re-executing \(\omega\) from \(s_0\) passes every check.

V = Vstate ∪ Vtrace ∪ Vout · replay or discard
Data edge — output feeds input (69%) State edge — precondition on \(s_t\) (25%) Retry edge — recovery after failure (6%) Mean out-degree 2.3 · max 56 · 66.2% of trajectories span ≥ 2 service families

Scaling

More data helps.
More environments help more fundamentally.

Both scaling axes use the same Qwen3.6-35B-A3B backbone, training recipe and evaluation protocols — only the amount of ToolSpace data, or the number of environment clusters it is drawn from, changes. Zero denotes the untuned backbone. Lines below are read directly from the paper's scaling figure (five benchmarks).

(a) Data scaling

Training-data fraction · 0 → 1/16 → 1/8 → 1/4 → 1/2 → full

The full dataset is best on all five benchmarks, and the last doubling (1/2 → full) still adds +4.6 on AutomationBench — the current synthesis scale has not hit its returns ceiling. Each fraction adds newly witnessed tool chains, not more copies of the same ones.

(b) Environment scaling

Training-environment fraction · 0 → 1/16 → 1/8 → 1/4 → 1/2 → full

AutomationBench jumps 9.2 → 33.8 between 1/16 and 1/8 environments: new clusters contribute new cross-environment edges, so space breadth is the limiting factor at low coverage (≈ +4 pts per doubling beyond 1/8). τ³-Bench Banking, which relies on a narrower stateful tool set, gains most only at the full environment set (19.6 → 34.0).
